# OpenVisio V43.26 — silhouettes and component detail for infrastructure shapes

**Author:** Abdelhalim Talbi  
**Candidate branch:** `develop/v43.26-infrastructure-glyphs-20261026`  
**Qualification date:** 26 October 2026

## Functional change

The native Python renderer and SVG exporter now share the same model-space vector primitives for nine infrastructure categories: server, storage array, SAN switch, generic switch, network switch, NAS, firewall, database and application. Recognised nodes receive a category-specific body silhouette, a small pictogram and internal detail primitives. Stable canvas tags and SVG data attributes support retained rendering and regression assertions.

The glyph layer is visual only. Node centre, width, height, hit-testing rectangle and connector attachment geometry remain the canonical geometry used by the model and router. Unknown, legacy group and very small shapes fall back to the previous rectangular body rather than being silently reclassified. The vectors are original schematic symbols; they are not Microsoft Visio stencils, vendor artwork or a claim of exact vendor-specific appearance.

## Implementation

- `03-Sources/openvisio/shape_icons.py` and `python/openvisio/shape_icons.py`: common shape outlines, pictograms and details.
- `render.py` mirrors: Tk canvas polygons/lines with retained tags; compatibility rectangle kept transparent for older integrations.
- `export.py` mirrors: SVG polygons and paths with `data-openvisio-node-body`, `data-openvisio-node-icon` and `data-openvisio-node-detail` attributes.
- `test_shape_icons_v4292.py`: existing Tk-capture/SVG parity checks extended for body silhouettes and details.
- `test_infrastructure_glyph_details_v4326.py`: regression checks for distinct shape paths, detail containment, fallback behaviour and unchanged routing/hit-test bounds.

## Qualification boundaries

Unit and synthetic renderer/export tests can prove that OpenVisio emits the intended vector primitives. They cannot prove pixel-level equivalence to Microsoft Visio. This candidate does not claim a Microsoft Visio Desktop round-trip, a manual interactive Windows acceptance run or a vendor-stencil fidelity qualification. Windows native portable/installer status is reported only from the matching GitHub Actions run; see the bundled qualification JSON and CI logs.

## Reproducibility

The Windows candidate workflow pins Git blob identities for the changed engine and tests, checks source/test mirror parity, runs the full Python suite from an independent checkout, builds the portable executable and Inno Setup installer, and audits the cumulative ZIP against the exact Git tree. The resulting archive must be treated as qualified only if the workflow for the final head commit succeeds.
